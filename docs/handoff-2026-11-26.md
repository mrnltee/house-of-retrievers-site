## 1. The project in one paragraph

House of Retrievers ("The House of Retrievers' Society, Inc.", HoR) is a
small SEC-registered Philippine nonprofit of Golden Retriever and Labrador
families who run charity events, outreach and volunteering. One Next.js 16
app on Vercel serves five hosts: the main site (`www.`), events and RSVPs
(`events.`), a large admin module (`admin.`), a press hub (`media.`), and
a retired countdown host that redirects. Data is in Neon Postgres; email goes
through Resend; event albums are on Cloudinary. The owner is a **UI/UX
designer** who works in Figma and uses AI for building, research and expert
validation of design work.

## 2. Who decides what

- **The owner decides product, wording, facts and anything public.** Each
  CLAUDE.md bullet ends with who asked and when, e.g. `(23 Nov 2026, owner)`
  or `(17 Nov 2026, design review)`. Keep that habit: it is how a later
  assistant knows whether something is a firm decision or a suggestion.
- **"Owner's choice" / "owner's decision"** in CLAUDE.md means the owner
  chose between options. Don't reopen it unless they ask.
- **Facts come from HoR, never from the AI.** Places, head counts, peso
  amounts, beneficiaries, sponsor names, dates. When a fact is missing, leave
  a placeholder or a "to confirm" list and ask. Example: the media hub stories
  (`app/lib/mediaStories.mjs`) each carry a `confirm` list; HoR answered it on
  23 Nov and only then was the detail added.
- **Protected copy lines** (listed in AGENTS.md §7) are never rewritten.
- **Brand artwork** (the two-dog logo) is never redrawn. See CLAUDE.md
  "Non-negotiable brand constraints".

## 3. The two kinds of request

**A. Owner feature requests** ("add a Type column to the Brand tracker",
"let puppies' ages be in months"). The usual loop:

1. Restate what will change for the visitor or admin, in plain words.
2. If it's a new screen and the owner wants design first, design it in their
   Figma file (pages "Events prototype", "Foundations & notes",
   "Admin module (Oct 2026)"), then build to match.
3. Build it. Pure rules go in a `.mjs` file with a `.test.mjs` next to it.
4. Database change → a new additive migration (next number in §6).
5. Update the feature's bullet in CLAUDE.md, in the same style.
6. Commit, push, open a PR; tell the owner what changed and how to try it.

**B. Design reviews** ("review this page", "suggest based on your
expertise"). The owner asks the AI to act as a **senior product designer**:
critique, recommend, then fix. What a review here has covered:

- Hierarchy (what's the main action; is the primary button the only gold one).
- Layout at **1440 / 768 / 375–390 px**; wide admin tables become cards on
  phones (`.stack-table`).
- Typography: `text-wrap: balance` for headings, `pretty` for paragraphs; an
  orphan count (one-word last lines) before and after, aiming for 0.
- Touch targets ≥ 44 px, labels ≥ 12 px, WCAG 2.2 AA contrast (gold *text* on
  light backgrounds uses the darker ink, about `#7a5a1c`).
- Keyboard, focus return in dialogs, `prefers-reduced-motion`, WCAG 2.2.2
  pause controls on anything that moves by itself.
- Copy in HoR's voice (AGENTS.md §7: warm, plain, to the person, never
  machine voice).
- Missing states: empty, loading, error, "nothing waiting".

The result is recorded as a CLAUDE.md bullet named "… review (date, design
review)", listing what was fixed and the CSS block name (e.g. "Guest tracker
review" in `admin.css`), so the next reviewer knows it was already looked at.

Give a **recommendation, not a menu**. When the owner asks "what do you
think?", say what you'd do, why, and the trade-off. When they pick from
options (e.g. "direction C + A's fact strip" for the donor section on 26
Nov), record the choice.

## 4. How replies to the owner should read

- Lead with what changed for a person using the site, then where to see it
  (URL or screenshot). Skip the code tour unless asked.
- Short. Plain English (they sometimes write in Filipino or Taglish; answer in
  English unless they write fully in Filipino).
- Say clearly what was **not** done or **not** verified.
- Ask before anything irreversible, anything touching money, live data,
  production, or emails to real people.

## 5. Engineering habits that keep it consistent

These are spelled out in AGENTS.md §7; the ones that matter most:

- Plain JSX/JS, no TypeScript. Asia/Manila time everywhere.
- Anything that can run out (last slot, early-bird places) is checked under
  the event row lock on the server, never in the browser.
- Every admin button that changes something goes through a confirm dialog
  (`ConfirmButton.jsx`); a test fails otherwise. Several other "guard" tests
  exist the same way: icons must be lucide (`iconGlyphs.test.mjs`), external
  links open in a new tab (`externalLinks.test.mjs`), every activity-log key
  has a label, every sidebar item has an icon, CSS braces balance.
- Reuse what exists before inventing: `EditDialog` for edit windows,
  `ListSearch` for search-as-you-type, `TrackerTools` / `SelectionBar` for
  tick-and-act lists, `ScrollRow` for sideways rows, `pop-menu` for More menus,
  `HowTo` guides on every admin page.
- Without `DATABASE_URL` the public site must still work (fallback content).
- Photos never go to Vercel Blob (the Instagram token lives there).
- Every email goes through `sendEmail`, which CCs HoR's inbox.
