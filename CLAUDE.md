# Claude Code handoff

This file is the product spec, shared with Codex. `AGENTS.md` has the workflow (staging first, push to main only when the owner says so, shared database), conventions and open items; read both. When a feature changes, update its bullet here.

## Product goal

Refactor and continue the House of Retrievers concept site without changing its approved brand direction. The primary visitor action is joining the community as a member, volunteer, or partner.

## Non-negotiable brand constraints

- Preserve the exact supplied two-dog silhouette logomark. Do not redraw, reinterpret, or replace either dog.
- Keep the icon on the left and the complete text mark on the right.
- On dark surfaces the logo uses the reverse artwork (white Labrador and wordmark) so the Labrador, wordmark, paw, and lines remain readable.
- The Golden Retriever stays in the original brand gold.
- Logo artwork (Oct 2026): "The House of Retrievers Society Inc." Source SVGs are in `brand/` (see `brand/README.md`); the site uses PNGs rendered from them on the 1396 x 564 canvas. Logo inks follow the artwork: gold `#AD8330`, Labrador `#0D0D0D` on light and `#F2F2F2` on dark (`--hor-gold` / `--hor-lab`).
- Seasonal themes are parked (14 Oct 2026). The public theme runtime, API and Admin screen are not active. Migration 024 remains because it was applied additively to the shared database; its unused `seasonal_themes` table must not be dropped or the migration rewritten. The preserved implementation lives on `codex/seasonal-theme-parked` if HOR revisits it with an approved motion design.
- Primary palette: near-black `#0D0D0D`, retriever gold `#A78440`, white, warm ivory, and restrained taupe.
- Maintain accessible contrast and respect `prefers-reduced-motion`.
- The header, footer and events header use `app/components/LogoMoments.jsx`. Every 7–15 s one dog, or both, has a short moment and returns exactly to the static pose, so there is no visible swap. Light mode plays daytime moments (wag, look up, give paw, perk, sniff); dark mode plays evening ones (doze, tail thump, stargaze, snuggle). `tone` is the surface: "dark" uses the white Labrador and reverse wordmark, "light" the near-black ones, "auto" (footer) follows the colour scheme. The dogs are an inline SVG traced from the reverse logo (`app/lib/logoMomentsRig.mjs`; never hand-edit the paths, rebuild with `python3 scripts/logo/extract_logo_layers.py`); the wordmark is the supplied art with the dogs cleared (`public/house-of-retrievers-wordmark-*.png`). Each moving part is the dog's path clipped to `clip` and rotated about `origin`, with `cut` masked from the still body; keep rotations within about ±16° so the overlap hides the joint. Moment sets and timings: `app/lib/logoMoments.mjs`; keyframes: `globals.css` "Logo moments", all starting and ending at `rotate(0)`, which is what makes the hand-off seamless. Off under reduced motion, off-screen and in hidden tabs; unprompted moments stop after 8 (WCAG 2.2.2), hover/focus still plays one.

## Events subdomain

`events.houseofretrieversph.org` is served by this same project, not a second app.

- `proxy.js` calls `routeEventsRequest()` in `app/lib/eventsHost.mjs`. On the events host every page path is rewritten to the `/events` routes, so `events.…/` renders `app/events/page.jsx` and the address bar keeps the subdomain.
- One address per page: `events.…/events/x` redirects to `events.…/x`, and `www.…/events/x` (or the apex) redirects to the subdomain. Preview deployments and localhost are left alone so `/events` can be reviewed before the domain is live.
- API routes, `/_next` and any path with a file extension are not rewritten, so the join form, images and `robots.txt` work on both hosts.
- Links from the events pages back to the main site must be absolute (`HOME_URL`). The main header links to `EVENTS_URL`.
- Event data lives in `app/content/events.js`. Add an event only when HOR has confirmed every field. An event moves to "Where we have been" and stops taking RSVPs once it has ended (`hasEnded` in `app/lib/eventTime.mjs`: the end time in Manila; three hours after a start time given alone; midnight for all-day or untimed events); the events pages revalidate every 5 minutes.
- Local check: `npm run build && npm start`, then open `http://events.localhost:3000`.
- Go-live order: add `events.houseofretrieversph.org` in Vercel → Project → Settings → Domains first (DNS is on Vercel, so the record and certificate are automatic), then merge. Merging first would send the header's Events link to an address that does not resolve yet.
- Search Console: use a Domain property for `houseofretrieversph.org` so the subdomain is covered and the cross-host sitemap entry is accepted.

## Admin module (Phase 1)

`admin.houseofretrieversph.org` is served by this project from `app/admin/`, routed like the events subdomain (`app/lib/adminHost.mjs`). On previews and localhost it lives at `/admin`. The plan is the "Admin module plan" tab of the HOR audit doc; screens are on the "Admin module (Oct 2026)" page of the HOR Figma file.

- **Database:** Neon Postgres (free), added through Vercel, sets `DATABASE_URL`. Schema in `db/migrations/*.sql`. `npm run build` applies new files first when `DATABASE_URL` is set (each once, recorded in `schema_migrations`, under an advisory lock, over `DATABASE_URL_UNPOOLED` when present). Locally: `npm run db:migrate`. `app/lib/db.js` keeps DATE columns as `YYYY-MM-DD` strings on purpose; a JS Date shifts the day by the server's UTC offset.
- **Without `DATABASE_URL` the public site behaves exactly as before:** events come from `app/content/events.js`, the Support panel shows its built-in preview, RSVPs are off. Don't break that fallback.
- **Sign-in:** next-auth v4, Google only, JWT sessions signed with `NEXTAUTH_SECRET`, or, when that is unset, a key derived from `DATABASE_URL` (`sessionSecret()` in `app/lib/admin/auth.js`); `NEXTAUTH_URL` = the admin URL in production. Only active rows in `admins` or emails in `ADMIN_OWNER_EMAILS` get in; env Owners are upserted with the Owner role on sign-in. While the Google app is in Testing, every admin must also be a Google "test user".
- **Roles** live in `app/lib/admin/roles.mjs` and are re-read from the database on every page and action (`app/lib/admin/guard.js`). Never trust roles from the cookie or the form.
- **Payment details** change only through `payment_change_requests`: a different Owner approves, after a sign-in in the last 10 minutes, with the "checked against HOR's records" box ticked. Switching a method off is immediate. The database also refuses a self-approval and a second pending request per method.
- **Event photos** are uploaded in the event editor and framed there at the card's 16:10 (`PhotoCropper.jsx`: drag, zoom, pinch, arrow keys). The browser sends the 1600×1000 crop plus the uncropped original (longest side 2400) and the framing; `events.image_source` / `image_crop` keep those so "Adjust framing" re-crops from the original, not the saved crop. All are stored in the `event_images` table and served by `/api/event-image/[id]` with a one-year immutable cache. A new upload gets a new id; nothing is edited in place. Not Vercel Blob, for the same reason as Join photos.
- **Prices:** `events.price_tiers` (`[{label, amount, from?, until?, limit?}]`, up to 6, ₱; 0 = free) is the record. A tier can also be limited to the first N registrants ("Only for the first registrants"; e.g. an early bird for the first 20): registrations are counted per ticket by label + amount (`tierKey`; not cancelled, so pending payments and the waitlist count and a cancellation frees a place; `app/lib/ticketCounts.mjs`), under the event row lock in `/api/rsvp`; once all N are taken the tier isn't offered, the card shows the other prices, and the event page marks it "Sold out". The RSVP shows "First 20 registrants · 3 left". A tier can have a sale period ("Sale period" in the editor, Manila date + time; e.g. an early bird that ends on a date): outside it the tier isn't offered on the RSVP (`tierAvailable` / `activeTiers` in `app/lib/prices.mjs`; `chooseTicket` takes an index into the full list and refuses an ended tier, except for an admin adding someone by hand), the card's price shows only tiers on sale, and the event page lists ended ones struck through (`tierWindow`: "Until Oct 10, 11:59 PM", "Ended Oct 10"). `cost` is saved as the summary the cards show (`priceSummary` in `app/lib/prices.mjs`: "Free", "₱795", or lowest–highest). Events saved before tiers fall back to their `cost` text. The price sits in the card footer with RSVP, not among the badges.
- **Extra photos:** `events.gallery` holds up to 3 more pictures (4 with the cover), uploaded one at a time by `uploadEventPhoto` in `app/admin/eventTools.js` when picked (a save would otherwise exceed the server-action size cap). The event page shows the uncropped cover then these, whole, in `EventMedia`; its header band is the cover, blurred.
- **Fill per picture:** `events.image_fit` (cover) and each gallery entry's `fit`: `fit` (whole, blurred backdrop), `fill` (cover uses the framed crop), `tile` (repeated). Picked with `FitPicker.jsx`.
- **Preview:** the editor's Preview button (`EventPreview.jsx`) builds the event from the unsaved form through `toPublicEvent` and draws it with the public `EventDetailPage` / `EventCard`, at desktop or phone width. The event page lays itself out with a container query on `.event-detail-wrap` (not screen media queries), which is what lets the preview show the true phone layout inside a desktop window. Keep new event-page layout rules as container queries.
- **Event page layout (Figma "Event page — UX pass", 11 Oct 2026):** two columns from 960 px of page width (poster left, sticky; facts, price card with RSVP, about, what's included, map, hashtags right); a phone bottom bar with price + RSVP that hides while the main card is on screen. `venue_address` is the smaller line under the venue name; `included` is the "What's included" checklist; a placeholder beneficiary (TBA, "To be named"…) is never shown and doesn't count for publishing (`isPlaceholder`). Add to calendar: `app/lib/calendar.mjs` (Google link + .ics, Asia/Manila).
- **All day and supporters (12 Oct 2026):** `events.all_day` hides and clears the times (shown as "All day", a date-only calendar entry). `events.partners` / `events.sponsors` are up to 8 names each, picked from People (Partner / Sponsor, organization first) or typed (`SupportersField`), shown on the event page under "With thanks to".

Migration 025 widens the old code constraint so existing three-letter IDs keep working; an old ID is upgraded only when an admin deliberately saves that record, then the four-letter code is fixed. `category_label` is an optional user-written relationship label such as “Venue partner”; it is shown in admin and in the public detail panel, without inventing a fixed category list. Sponsor tier (`TIERS` in `app/lib/supporters.mjs`: Pack Leader / Best Friend / Good Pup — names are HOR's to change, keys stay), logo (stored in `event_images`, resized in the browser to 800 px WebP/PNG by `LogoField`), website, Instagram, blurb (≤200), what they gave (cash / in-kind / services / venue, per year), private contact and notes. Admin: `/supporters` has Cards and List views, search, relationship-label, kind and status filters; `/supporters/[id]` is the record; actions live in `app/admin/supporterActions.js`; "Make a sponsor record" is on a Sponsor/Partner in People. Public only when `isPublic` (confirmed + show_on_site + logo + blurb); Ended switches it off. Amounts are public (HOR's transparency promise) only once `amounts_agreed_at` is set ("The sponsor knows these amounts are public"). The home page section `Supporters.jsx` (above FinalCta, `#partners`; option A, the menu is unchanged) reads `/api/supporters` (5-minute edge cache, no contact data): partners, sponsors by tier, a totals bar, a detail dialog, and "Become a sponsor or partner" (opens Join as Sponsor). Logo tiles are about 200px wide; each partner or sponsor group becomes a keyboard-accessible five-item-at-a-time carousel when it has more than five logos. `?supporter=<slug>` opens a panel; event pages link supporter chips there (`supporterLinks` in `app/lib/publicSupporters.js`). Events link to records by name in their Partners / Sponsors fields, which suggest record names first.
- **Event payments (12–13 Oct 2026, Figma "Event payments" on the Admin module page):** on a paid event (`fee_required`) the RSVP asks for a ticket (`events.price_tiers`, public `tickets`; `chooseTicket`), stores `ticket_label` / `ticket_amount`, and holds the spot with `fee_status` `waiting` ("Payment pending"; the hold expires per the event's payment-hold setting, see "Payment hold expiry" below, and HOR confirms backouts by chat in the meantime). The registrant pays by the approved channels (Payment settings, now with GoTyme) and uploads method, reference number, amount and their confirmation screenshot (`PayStep.jsx`, in the RSVP modal and on the pass page; `/api/rsvp/proof`) → `review` ("To check"); screenshots go in `payment_proofs` (private, served to admins by `/registrations/proof/[id]`; older uploads kept). The spot-held email deliberately says "approved payment methods" instead of listing channel names, so switching Bank, GCash, Maya, GoTyme or QR Ph on or off cannot make the email stale. Payment settings can also partly hide a mobile or account number on public surfaces (`091 •••••• 89` / `12 •••••• 90`); full is the default, and changing this display setting follows the same two-Owner review as any payment-detail change. An admin with `registrations:fees` opens the registration (`/registrations/[eventId]/r/[regId]`): Approve (tick "found it in HOR's history") → `paid` and the QR pass is emailed; Ask for a new receipt (reason, presets in `REJECT_REASONS`) → `rejected` and the reason is emailed; Mark paid by hand (cash etc.); Attach / replace a receipt. Every registration-payment action checks the capability before reading the registration. "+ Add registration" (`/registrations/[eventId]/add`, `registrations:edit`) adds people who paid before the system (Paid / Pending / No fee; over capacity allowed). The same reference twice in one event is flagged (`referenceKey`). No QR before approval: the pass page (`passState`) shows the pay step / "under review" / the reason, and the door (`checkInOutcome` → `unpaid`) says "Payment not confirmed". Payment wording is event-specific through `paymentNotice(event)`: charity events keep the approved fundraising notice; other paid events explain that early-bird rates are limited, may end at the sale-period or first-N limit, and the regular rate applies afterward. `events.onsite_payment` is an optional editor setting that adds that on-site payment, if available, is charged at the regular rate; it is off by default and does not change any existing event until the venue confirms it. The wording appears on the RSVP, payment step, pass page and payment emails. Rules and labels: `app/lib/eventPayments.mjs`; admin actions: `app/admin/registrationActions.js`; emails: `app/lib/passEmails.js` (`sendPass` with the QR picture from `/api/pass-qr/[code]`, `sendSpotHeld`, `sendReceiptRejected`, `sendWaitlisted`). Migration 018 for payments, 023 for the event setting.
- **Registration counts and pricing (13 Oct 2026):** the event editor's "Payment basis" keeps the existing one-ticket-per-registration default and can switch to per person, per furbaby, or a human + furbaby bundle. Bundle tiers record how many people and furbabies one bundle includes. RSVP and admin add/edit calculate and save `human_count`, `furbaby_count` and `amount_due` under the same event-row lock used for ticket availability. Admins with `registrations:edit` can edit name, email, furbaby, attendee counts, ticket and consent details; a saved edit sends no email unless explicitly selected. A paid registration may be recalculated only when its existing `pay_amount` exactly matches the new amount; this allows a safe correction such as 3 people × ₱695 = ₱2,085 while preserving Paid status, reference, receipt and QR pass. If an older paid row has a stale saved snapshot, `registrations:fees` can use the dedicated Correct saved amount action; it updates only `amount_due` after an exact payment match and sends no email. Other paid amount changes remain blocked. Unpaid amount changes return payment to pending and ask for new proof. The actions are in `app/admin/registrationActions.js`, the pure formulas and capacity rules are in `app/lib/registrationPricing.mjs` and `app/lib/eventCapacity.mjs`, and the public/admin forms are in `app/components/RsvpModal.jsx`, `app/admin/(app)/registrations/` and `app/admin/(app)/events/`. Migrations 021 and 033.
- **Additional dog companion pricing (13 Oct 2026):** a paid event can use the "Per person + dog companion" basis. The editor sets how many furbabies each human ticket includes and an optional extra-furbaby fee. `amount_due` is the human ticket total plus extra dogs beyond the included allowance; for this basis, a first-N tier limit counts people (so two people use two Early Bird units). Existing events default to zero included companions and no extra fee, so their behavior is unchanged. Migration 022; the formula remains in `app/lib/registrationPricing.mjs` and the event fields are saved by `app/admin/actions.js`.
- **Ticket-specific attendance pricing (15 Oct 2026):** a paid event can use the "Ticket-specific attendance rules" basis, so each price tier is explicitly either **Hooman only** or a **Furbaby package**. Hooman-only tickets charge their tier amount per person and reject furbaby entries. A furbaby package charges per furbaby, includes the editor-set number of people per furbaby, and adds the editor-set fee for each additional person. The editor lays each tier out as a stacked card—name and amount first, rule and inclusions second, sale settings last—so the rules remain legible at every width. The RSVP API and admin add/edit actions recalculate and enforce the rule server-side under the existing event lock; current pricing bases and events stay unchanged. Migration 026; the formula is in `app/lib/registrationPricing.mjs`.
- **RSVP controls and vaccination records (15 Oct 2026):** the event editor has a clear **Registration is open** switch (off means the public event remains visible but `/api/rsvp` refuses new RSVPs), plus an optional RSVP button label for public RSVP entry points. The usual labels remain when it is blank, and paid events retain “Continue to payment” so the payment step is never obscured. An editor may also show an **optional** vaccination-record photo input for one event. Participants can submit without a photo; when provided it is browser-resized, stored privately in `registration_vaccination_records`, and is visible only to authorised admins on the registration detail page. It is never public, never emailed, and never sent to Vercel Blob. Migration 027; editor validation/public mapping lives in `app/lib/admin/events.mjs`, submission in `/api/rsvp`, and the private image route is `/admin/registrations/vaccination/[registrationId]`.
- **Participant form configuration (16 Oct 2026):** the event editor can enable optional RSVP questions and arrange them, and the Preview dialog includes an RSVP form view. The configuration is stored on the event with migration 029 and defaults safely for older events.
- Hooman-only ticket forms hide all furbaby name/count fields; the server still enforces zero furbabies for that ticket.
- **Capacity units (17 Oct 2026):** capacity and pricing are separate choices. The event editor's Registration card says exactly what one RSVP consumes: one slot per registration (the safe default for existing events), one slot per hooman, or one slot per furbaby. A registration with 3 hoomans therefore uses 3 hooman-capacity slots; a furbaby-capacity event requires at least one furbaby and a registration with 2 furbabies uses 2 slots. The selected capacity basis is enforced under the event row lock in `/api/rsvp`, reflected in public full/few-spots status, admin counts, waitlist confirmation, restore and attendee-count edits. The amount still comes from Pricing and availability, and first-N Early Bird units still follow their ticket rule. Furbaby capacity needs every ticket to have a furbaby to count: `validateEvent` refuses furbaby capacity together with a ticket-specific attendance tier marked Hooman only. Pure rules and shared SQL live in `app/lib/eventCapacity.mjs`, with tests beside it. Migration 033 adds the backward-compatible `events.capacity_basis` defaulting to `registration`.
- Event acknowledgements (16 Oct 2026): an event can add a low-friction acknowledgement to its private RSVP page. It does not block RSVP, payment, QR issuance or check-in, and it sends no email. The participant confirms a checkbox and types the registered name; completion is stored on the registration with migration 030. Admin configuration is in the event Participant form section and status is shown on registration details.

- Consent templates: the first release includes reusable Simple acknowledgement and Safety + photo/video consent templates. An event selects one and can add its own introduction; the selected template key is stored with the event configuration.
- **Payment hold expiry (16 Oct 2026, lengths made configurable 17 Oct 2026):** a paid RSVP starts a `waiting` hold shown as a live countdown in the RSVP modal. ## Instagram feed and its token

The feed at `app/api/instagram/route.js` needs a long-lived Instagram token,
and those expire 60 days after they are issued. A running function cannot
rewrite its own environment variables, so the token does not live in one.

- The **live token sits in a private Vercel Blob**, `instagram/access-token.json`,
  read and written through `app/lib/instagramToken.js`.
- `INSTAGRAM_ACCESS_TOKEN` is only a **seed**. It is used until the first
  rotation writes a blob, and as a fallback if the blob cannot be read. After
  the first rotation it is stale and is no longer what the feed serves —
  replacing it changes nothing while the blob is healthy.
- A **daily cron** (`vercel.json` → `/api/cron/refresh-instagram-token`) trades
  the current token for a fresh 60-day one through `ig_refresh_token`, with no
  re-authentication. It returns early while the token is under 30 days old, so
  most runs cost nothing. Daily rather than monthly on purpose: monthly gave the
  rotation a single attempt, and one failure would have run out the clock.
- The cron route answers only to Vercel's signed call (`CRON_SECRET`).
- Blob reads go through the SDK with the CDN cache off. A private blob cannot be
  fetched from its URL, and a cached copy would hand back the token just replaced.

To recover if the blob is ever lost: generate a token, set it as
`INSTAGRAM_ACCESS_TOKEN`, redeploy, and the next cron run re-seeds the blob.

## Join photos

An optional furbaby photo is resized in the browser (`app/lib/resizeImage.js`,
longest edge 1600, quality 0.82) and travels as a base64 data URL through
`app/api/join/route.js` to the Apps Script, which files it in Drive and links
the sheet cell to it.

- Photos go to **Drive, not Vercel Blob**. Blob on Hobby cuts off access for
  thirty days once its limits are passed, and the Instagram token lives there —
  photo traffic must not be able to take the feed down with it.
- The folder is found by the id in the `PHOTO_FOLDER_ID` script property, so
  renaming it in Drive is safe. `PHOTO_FOLDER_NAME` is only the fallback.
- Files are **not shared**. They are personal photos offered to join a
  community; the owner opens them signed in.
- They cannot be displayed inside a cell. Google blocks `drive.google.com`
  URLs in `IMAGE()`, and the old `/uc?export=view` workaround now returns 403.
  Clicking the cell's link shows Sheets' own preview card, which works on a
  private file — that is the display. Making it work in-cell would mean
  publishing the photos.
- Adding a Drive call to the script needs the scope granted by hand: run
  `authorizeDrive` from the editor. Apps Script grants only the scope a run
  reaches for, so the function has to write, not just read.

## Media conventions

- Story media lives in per-section folders under `public/`: `1-purpaws/`, `2-better/`, `3-giveback/`.
- Camera originals stay local. `.gitignore` keeps `public/**/*.JPEG` and `public/**/MBY.mp4` out of the repo, so committed media is always the web-ready copy.
- Encode video as H.264 (`libx264`, yuv420p, `+faststart`). HEVC is hardware-gated and silently fails on Windows Chrome and Firefox, so it must not ship. Background loops sit at 1280–1600 wide, CRF 23–28, no audio track.
- Poster images are pulled from the video's own first frame, so the still does not jump to a different scene when playback starts.
- Keep photos near their rendered size: the family cards render around 410px wide, so the longest side belongs at 1440, not 4096.
